| AF-D36 | Accent tones for the rarer architectures | Teal for RISC-V and coral for PowerPC, as accent colours beside the existing x86, ARM and MIPS accents | Owner | Each architecture stays distinct with no extra artwork (AF-D17). Implemented (AF-D49). |
| AF-D37 | Terminal depth hand-off | `Terminal::set_depth` (default: ignore) is called by `run` once the depth is resolved, and `AnsiTerminal` uses it for its escapes | Assumed | The depth is decided inside `run`, after the shell has built its terminal, so an ANSI shell cannot otherwise know it. |
| AF-D38 | Unix runtime shape | No libc and no start files: `_start` is a `global_asm!` stub per architecture, the system calls are an `enum Sys` kept equal to `platforms/unix/syscalls.allow`, `memcpy` and its kin are volatile byte loops in `rt.rs`, and `link.ld` places code and data and drops unwind tables and notes. The program uses at most three system call arguments | Assumed | The binaries are 20 to 23 KiB with no sysroot, and the volatile loops keep the compiler from turning them into calls to themselves. |
| AF-D39 | Linux fact sources | Memory is `MemAvailable` of `MemTotal` (older kernels add free, buffers and cache), with `sysinfo` as the fallback; the CPU name falls back from `model name` to `cpu model`, `uarch`, a known Arm core, `Hardware` and `Model`; the Host row skips firmware placeholders such as "To Be Filled By O.E.M."; the user falls back to `/etc/passwd` by uid; the Display row stays empty | Assumed | Each fallback is a real file on a real board, and a placeholder is not a fact (AF-D20). |
| AF-D40 | Logo byte budget | 700 bytes per blob and 6 KiB (6,144 bytes) for all blobs together, enforced by the art generator from `art/logos.toml`; 7 KiB is the ceiling if the logos ever need more, raised by changing this record. The eight blobs are 2,026 bytes | Assumed | The drawn logos use under a third of 6 KiB, and the smaller figure keeps the tightest binaries (Win32 i586 at 16 KiB, Desk at 16 KiB) in budget; one figure replaces the 7 KiB and 6 KiB that disagreed. |
| AF-D41 | Logo size and layout width | Every picture is 36 × 24 pixels (36 × 12 cells) and every ASCII form at most 36 × 12, except `win32`'s ASCII form at 40 × 12, the single exception. The facts start at the information column, the logo's widest form plus a gap of 2 (38, or 42 for `win32` in every form), and the logo is drawn beside them only from information column + 34 columns: 72, or 76 for `win32` | Assumed | One grid for the family; the exception keeps the ReactOS output byte for byte, and one column per logo keeps plain and colour output aligned the same way. |
| AF-D42 | Tone mapping exceptions | At 256 colours each tone takes its nearest xterm cube or grey entry, except amber, which takes 221 because its nearest, 215, is orange's. At 16 colours amber and peach take orange (console 6) to keep the bands in order, night and umber take slate (console 8) by role, and soot is dropped at 16 colours and in mono. Umber and soot, used only by `desk`, are provisional until the owner reviews that logo | Assumed | Five distinct sun bands at 256 colours matter more than the closest match, and at 16 colours a band out of order or a doubled ring reads worse than a slightly farther colour. |
| AF-D43 | JSON schema 1 | Every key is always present and an absent fact is `null`; `desktop` sits between `display` and `terminal`. The first release adds AF-D34 as `schema` (the number 1, first), then after `resources` the strings `target` and `arch` and the numbers `uptime_seconds`, `memory_available_bytes` and `memory_total_bytes`. Implemented (the core emits them; the Linux and Win32 shells fill them) | Owner | A fixed key set is easier for scripts than optional keys, and the numbers go at the end so the existing keys keep their order. |
| AF-D44 | Build identity names | `--version` prints the target name of SPEC §2 (`linux-i586`, `windows-i586`, `dos-i386`), named by each shell, and the OS row prints the architecture name the system itself gives (`x86_64`, `i686`, `aarch64`, `armv7l`, `mips`), with no mapping to a fixed list; the owner rejected that mapping. Implemented: each shell names its target through `Platform::target_name`, and `--json` carries the same name as `target` | Owner | The names match the release files and the accent tones, so a version line or a screenshot names the build exactly. |
| AF-D45 | Win32 i586 shape | The Win32 shell is its own workspace over the core: console attributes on a console, no escape sequences on a pipe at any depth (the writer costs 1.3 KB of the 16 KiB budget), arguments from `GetCommandLineA`, the environment read once for the four names it uses, `GetFileType` before the console test, an architecture suffix on any OS row that is not a ReactOS release, and `/MERGE:.data=.rdata` so the headers stay one page | Assumed | The i586 build is 15.5 KiB of 16 KiB; the VT path in AF-WP13 can bring escapes back where a console accepts them. |
| AF-D46 | Logo decoder and forms | The core reads `.afl` blobs itself (`Logo::parse` validates the whole blob once, and every row decodes into a 48-cell buffer on the stack with each length checked, so a bad blob is an error and never a panic). A logo is drawn as half blocks when the terminal has them (UTF-8 on Unix; `Blocks::Cp437` for DOS) and the depth is not `None`, else as cells from the ASCII form (`#` a filled cell with colour), else, with no ASCII form, as filled cells from the pixels. 16 colours and mono use `PIXELS_LOW` when a logo has it. A tone transparent at a depth draws nothing, and two pixels that look alike at a depth are one `█`; in mono every drawn pixel pair is one `█` in the upper pixel's weight. `--logo <name>` is a name in `afterfetch_art::LOGOS` (unknown is a usage error), `Platform::default_logo` returns a name from `afterfetch_art::default_logo`, and the core's `Tone` is the art table's ids with 256-colour and truecolour taken from it | Assumed | One decoder serves every platform, the generated tables hold every colour decision (AF-D42), and an unvalidated blob can neither panic the program nor draw outside its row. |
| AF-D47 | Size budgets with the logos | Linux (x86_64 and i586) 32 KiB and Win32 i586 24 KiB, every binary keeping all eight logos (AF-D10). The logos cost 2,026 bytes of blobs, about 2.3 KB of art index and tone tables, and about 3.2 KB of decoder: Linux went from 22,864 and 20,916 bytes to about 29.5 and 26.3 KB, and the other budgets are unchanged | Owner | Every system keeps its own sun and `--logo` works everywhere, which the owner prefers to a smaller binary. |
| AF-D48 | Win32 build independent of the directory | The Win32 workspace reaches the core and the art crate through a `platforms/win32/crates` symlink to `../../crates`, and carries the `workspace.package` and `workspace.lints` tables the core inherits; the repro scripts build in three directories of different depth and length | Assumed | Cargo hashes a path dependency relative to the workspace root only when it is inside it; `../../crates/...` was outside, so the absolute checkout path reached the crate metadata, the symbol order and, through `/Brepro`, the timestamp. A symlink is the smallest change that keeps the Win32 workspace separate from the host one. The Unix shell is in the host workspace and was not affected. |
| AF-D49 | Output failure and accent in the core | `Terminal::flush` sends what is buffered and says whether every write worked; `run` calls it last and a failure makes the run exit 74 (`EXIT_OUTPUT`), unless it already has a usage error or a crash code. `output_exit(code, written)` is the same rule for a shell's own failure, such as a `/DUMP` file that cannot be created. The title's rule takes the accent of the architecture's family (x86 gold, ARM periwinkle, MIPS violet, RISC-V teal, PowerPC coral, anything else or unknown slate), found from the system's own name by prefix and looked up in the art crate's table; the displayed name is never changed. `Facts` carries the raw numbers, set together with their rows, and large numbers are written without a 64-bit division | Assumed | The core owns the exit code so every shell gets it the same way. Reading the family from `i686` or `armv7l` is a classification for a colour, not the mapping AF-D44 rejects. Win32 memory is capped at 4 GiB because `GlobalMemoryStatus` is; the 64-bit builds can lift it. |
| AF-D50 | Preview tool | `afterfetch-preview`, a host-only `std` crate with no dependencies, runs the real core's `run` over sample facts for every system and architecture, through a fake `Platform` and a terminal that records cells. It writes plain text, the exact ANSI bytes, HTML, JSON, or a PNG from a built-in 5 × 7 font and a small in-crate PNG encoder (fixed-Huffman deflate, indexed colour), and `--sheet` writes the contact sheet of the eight logos. It is never built for a target, shipped, or counted in a size budget; `make preview` and `make sheet` run it, and `make check` compiles, lints and tests it. Its tests reproduce the core's goldens byte for byte from the ReactOS sample | Assumed | AF-D30 realized. The preview shows every system, including ones with no binary yet, without running on it, and cannot drift from the program because it is the program. No crate was added, so `deny.toml` is unchanged |
| AF-D51 | 32-bit Arm: Thumb code and r12 | Linux armv7 and armv6 build with `-C target-feature=+thumb-mode` (Arm-mode code was 33.2 KB, over the 32 KiB budget; Thumb is 27.6 KB on armv7 and 28.1 KB on armv6). `syscall3` saves r7 in r12 and loads the call number through a scratch register, because Thumb reserves r7 as the frame pointer. `link.ld` drops `.ARM.exidx`, `.ARM.extab` and `.ARM.attributes`, which the prebuilt `compiler_builtins` carries with a reference to `rust_eh_personality`. `armv7` is told from `armv6` by the triple in `build.rs` (`arm_v7`), since Rust exposes no `v7` feature to `cfg`. The Arm smoke always calls the qemu-user emulator by name with `QEMU_CPU` set to a Pi-like core | Assumed | Keeps every Linux binary in 32 KiB (AF-D47) with all logos. ARMv6 (ARM1176) has Thumb-1 only, which the arm1176 emulation exercises. The compiler warns that `thumb-mode` is unstable; the build still passes because it is a warning, not a lint. |
| AF-D52 | Win32 64-bit builds, VT colour and the facts the preview found | The x86_64 and ARM64 PE files build from `platforms/win32/x86_64-win32.json` and `aarch64-win32.json` through `build.sh <arch>`: `no_std`, no C runtime, `rust-lld` as `lld-link`, relocatable with high-entropy ASLR (the no-relocations check stays i586-only). The x86_64 target is soft-float on the plain x86-64 baseline and carries no unwind tables; ARM64 keeps its default features and unwind tables, since it cannot run here. Their budget is **32 KiB** each, not the 20 KiB first written (they are 30,208 and 30,720 bytes): the same program is about 25% larger in 64-bit code and pointer tables, 20 KiB would need a smaller core, and Linux x86_64 has the same 32 KiB (AF-D47). The Pentium build is 24,576 of 24,576 bytes, with no spare. VT is **64-bit only**: those builds ask a console for `ENABLE_VIRTUAL_TERMINAL_PROCESSING` and UTF-8 (`SetConsoleOutputCP(65001)`), and when it accepts, true colour through the core's `AnsiTerminal` with half blocks, restoring the mode and code page at exit; the Pentium build keeps console attributes because the escape writer costs 2,048 bytes it does not have. A pipe gets no escapes at any depth, as before. The CPU row is the `CPUID` brand string (guarded by the EFLAGS ID bit on 32-bit), else the registry `ProcessorNameString` (all there is on ARM), else the vendor and family of a Pentium; the count is `GetSystemInfo`'s processors. Memory and uptime ask `GlobalMemoryStatusEx` and `GetTickCount64` by `GetProcAddress` on all three builds, with the 32-bit calls as fallback. The Kernel row on Windows 9x is `Windows 95 4.00.950` (98 and Me likewise). Every Win32 target builds with `panic=immediate-abort` | Assumed | The preview tool found three Win32 gaps against SPEC; this closes them. The 32 KiB budget and the Pentium's VT exclusion are the owner's to confirm. ARM64 and a real Windows 10 console are unverified locally (AF-D5). |
| AF-D53 | RISC-V 64 and PowerPC 64 LE Linux builds | `riscv64` and `ppc64le` build from the prebuilt libraries on the pinned 1.98.0 (no `build-std`, no `RUSTC_BOOTSTRAP`; inline `asm!` is stable on both) and run under qemu-user as `rv64` and `power8`, one emulated process at a time. RISC-V uses the generic table of ARM64; PowerPC uses its own `ioctl` requests (`TCGETS` 0x402C7413), the CR0.SO error flag and an ELFv2 entry that sets r12 for the callee's TOC set-up. `link.ld` places `.data.rel.ro*` in the read-only segment. The core reads the PowerPC CPU name from `cpu` | Assumed | Go for both targets; real hardware is unverified, as for Arm and MIPS (AF-D22). |
| AF-D54 | PowerPC 64 LE size budget | `ppc64le` is allowed 44 KiB (45,056 bytes), as MIPS is: it is 42,528 bytes, of which 37.5 KB is loaded (29.6 KB of code and read-only data plus 7.8 KB of tables). The same source is 31.1 KB on ARM64 and 30.0 KB on RISC-V. The code is about a third wider because every address costs a TOC-relative pair and the 64-bit sequences are longer; POWER10 PC-relative addressing would shrink it but is not a POWER8 baseline. Tried: the `.data.rel.ro` placement (saves a 4 KB page of padding, not code), explicit small and medium code models (the default is the smallest). Not tried: dropping logos (AF-D10, AF-D47) | Owner | Over 32 KiB and under the 44 KiB ceiling; the owner accepted the exception on 2026-11-27. |
| AF-D55 | FreeBSD: go | **Go (AF-D23).** `freebsd-x86_64` and `freebsd-aarch64` build from `x86_64-unknown-freebsd` and `aarch64-unknown-freebsd` (prebuilt libraries) as `no_std`, no-libc, static programs over raw system calls: `read`, `write`, `openat`, `close`, `ioctl` (`TIOCGETA`, `TIOCGWINSZ`), `getuid`, `__sysctl`, `clock_gettime`, `kenv`, `exit`, kept equal to `platforms/unix/syscalls-freebsd.allow`. FreeBSD reports a failure in the carry flag, which the stub turns into `-errno`; the kernel may change every argument register, so all are declared clobbered. The entry point is `rdi` (x86-64) or `x0` (ARM64), not the stack pointer. Its own layout, `link-freebsd.ld`, puts the headers inside the code segment, because FreeBSD's kernel refuses two segments that share a page. Facts: `kern.ostype`, `kern.osrelease`, `hw.machine`, `kern.version` (the Kernel row is its name, release and configuration, `FreeBSD 15.1-RELEASE GENERIC`), `kern.hostname`, `hw.model` and `hw.ncpu`, `hw.physmem` with free plus inactive pages of `hw.pagesize` (inactive pages are reclaimed before anything is refused), `clock_gettime(CLOCK_UPTIME)`, `kenv smbios.system.product`, `$USER` or `/etc/passwd`, `$TERM`, `$SHELL`. No package count (it needs the package database). Budget 32 KiB, as Linux (27.4 KB on x86_64, 26.9 KB on ARM64), not the 24 KiB SPEC first gave. Tested in the official 15.1-RELEASE `BASIC-CLOUDINIT-ufs` amd64 image under QEMU with KVM; the plain `ufs` image has no serial console and nothing to log in with, so the harness gives the cloud image a `cidata` disc whose nuageinit `runcmd` turns the serial login into an automatic root login. `freebsd-i686` is not built: the 32-bit compatibility layer would only run it, and FreeBSD i386 is not an install target anyone has asked for | Assumed | The first run found each of these: an exec the kernel killed with SIGABRT (overlapping segments), a crash from a register the kernel changes, and a wrong entry pointer. The tested path is what the smoke covers: plain, `--json`, the four colour depths and exit 74 on a closed standard output. Swap: the i686 build, a different Kernel row, or the 24 KiB budget would each be a small change. |
| AF-D56 | macOS: written, built, never run | `macos-x86_64` and `macos-aarch64` build from `x86_64-apple-darwin` and `aarch64-apple-darwin` as `no_std`, `no_main` programs whose `main` is the C entry point, importing from `libSystem` only the functions `os/macos.rs` declares (`write`, `read`, `open`, `close`, `ioctl`, `sysctlbyname`, `gettimeofday`, `getuid`, `_exit`, `__error`) and the memory routines, through a hand-written `libSystem.tbd`; no Apple SDK. Facts: `sysctlbyname` for the version, kernel release, host name, model, CPU brand, core count, memory (free plus speculative pages) and boot time; `$USER`, `$TERM_PROGRAM`, `$SHELL`. No Display row. Flags: `ld64.lld`, `-no_data_const` (an arm64 page is 16 KB and a read-only data segment cost a page, 67.3 KB against 50.7 KB), `-no_uuid` (lld hashes the output path into the UUID, which broke byte-identical builds). 37,808 bytes on x86_64 and 50,736 on arm64, inside the 64 KiB of SPEC §11. The `macos` job in `.github/workflows/ci.yml` builds, structure-checks, runs (arm64 natively, x86_64 under Rosetta 2) and reproduces both on `macos-15`, with no secrets; **nothing has run on macOS**, so dyld accepting a binary with no `LC_UUID` and the stub's SDK version, the arm64 signature and every `sysctlbyname` name remain unverified | Assumed | The owner decided macOS is CI-only (AF-D5); the build and its structure checks are what can be done here. Swap: if dyld refuses the binary, drop `-no_uuid` and give up byte-identical output, or link with Apple's linker on the runner. |
